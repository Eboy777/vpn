# Техническое задание MVP браузерного VPN-сервиса

**Версия:** 3.1
**Формат:** Chrome-расширение + GOST HTTPS Proxy  
**Масштаб MVP:** до 1 000 зарегистрированных пользователей  
**Основной протокол:** HTTPS CONNECT через GOST  
**Дата:** 09.08.2026

Документ содержит минимальный объём требований, необходимый для разработки и приёмки MVP.

### Утверждённые изменения v2.4–v3.1

1. Telegram deep link, polling привязки и постоянная авторизация устройства используют три независимых секрета.
2. GOST-ноды получают версионированный snapshot credentials с ограниченным сроком действия, применяют его атомарно и подтверждают применённую revision. После истечения snapshot пользовательские credentials автоматически закрываются.
3. Расширение обращается к backend через два публичных reverse proxy. Оба proxy должны быть развёрнуты и проверены до тестирования и deployment расширения.
4. Создание платежа, обработка webhook и приём результатов канарейки идемпотентны.
5. Production-платежи запрещены до письменного решения по фискальным чекам, налогам и возвратам.
6. Telegram-бот получает update через webhook. Один стабильный webhook-домен обслуживается обоими существующими API proxy; DNS health-check исключает недоступный proxy. Отдельный третий VPS не требуется.
7. Лимит — 3 активных устройства на пользователя. Для MVP действует один тариф: 299 RUB за 30 дней.
8. Поддерживаются текущая и предыдущая стабильные major-версии Chrome и Яндекс Браузера на дату релиза; точные номера фиксируются в release evidence.
9. Backup: RPO не более 24 часов, RTO не более 4 часов.
10. Token hashes — HMAC-SHA-256 с раздельными versioned keys; proxy-пароли — AES-256-GCM с уникальным nonce, key ID и AAD=`user_id`; Robokassa — SHA-256 согласно настройкам магазина.
11. Канарейка проверяет минимум два независимых HTTPS target каждые 60 секунд. Три последовательных подтверждённых node-specific ошибки блокируют ноду; три последовательных успеха делают её готовой к восстановлению, но возврат в `active` подтверждает администратор.
12. Robokassa ResultURL использует POST, Password #2 и ответ `OK{InvId}`. Нормативный wire-contract — `docs/API_CONTRACT.md` v1.
13. Этап 1 использует отдельный API process и один scheduler/worker под PostgreSQL advisory lock. Повторяемые фоновые действия сохраняются в transactional outbox. Токены нод и канареек хранятся в отдельных versioned auth-таблицах со статусами `current/next/revoked`.
14. Общие для всех API-процессов pairing rate limits хранятся в PostgreSQL только под HMAC-hash субъекта. Счётчики имеют минутные/часовые окна и автоматически очищаются выделенным worker после retention; IP, pairing token и другие raw-секреты в таблицу не записываются.
15. Безопасный bootstrap и planned drain используют промежуточные состояния `warming` и `quiescing`: в них нода получает полный snapshot, но не участвует в назначении пользователей. Это закрывает обнаруженное окно между включением ноды и первым ack.
16. Origin доверяет `X-Forwarded-For` только двум точным WireGuard peer-адресам API proxy. Каждый публичный proxy перезаписывает, а не дополняет этот заголовок, не журналирует URI, Authorization или body; FastAPI публикуется только на WireGuard-адресе origin.
17. Sync-agent использует исходящий long polling snapshot endpoint: новый пользователь обнаруживается без периодической 30-секундной паузы. Backend-worker контролирует подтверждённый lease, heartbeat и новый ack; после трёх пропущенных 15-секундных ack-окон либо 75 секунд без heartbeat переводит active-ноду в `blocked` и переназначает пользователей.
18. Интерфейс этапа 6 следует утверждённым макетам Virgo: на первом экране отсутствует слоган `Unblock your digital world`, в настройках не показывается `device_id`, а ссылка на пользовательское соглашение присутствует, но активируется только после публикации отдельного документа.
19. Если оба control API недоступны, расширение сохраняет последний уже применённый proxy максимум 300 секунд и никогда не позже известного `access_expires_at`; затем снимает proxy. `Retry-After` и offline deadline хранятся локально и переживают выгрузку Manifest V3 service worker.

## 1. Цель и границы MVP

Создать браузерный сервис, который перенаправляет трафик Chrome и Яндекс Браузера через удалённые HTTPS-прокси GOST. Пользователь устанавливает только расширение, привязывает его к Telegram и включает VPN одной кнопкой.

- Пробный период — 24 часа после первой привязки Telegram.
- Оплата — через Robokassa; после оплаты доступ продлевается автоматически.
- Для бесплатного пользователя нода выбирается автоматически.
- Платный пользователь может выбрать доступную локацию вручную.
- Сервис проксирует только браузерный трафик, а не всю операционную систему.
- Marzban, Xray, VLESS, WASM, локальный клиент и отдельный установщик не используются.

## 2. Архитектура

```text
Chrome-расширение -> API proxy A / API proxy B -> FastAPI -> PostgreSQL / Telegram / Robokassa
Telegram -> bot.example.com -> DNS health-check -> API proxy A / API proxy B -> FastAPI/Telegram-бот
Chrome-расширение -> GOST HTTPS-нода -> Интернет
```

| Компонент | Назначение | Размещение |
|---|---|---|
| Chrome-расширение | Привязка устройства, включение и выключение прокси, фоновая проверка доступа | Chrome Web Store / ZIP для теста |
| Два API reverse proxy | Два публичных HTTPS-входа к одному backend; fallback для расширения | Отдельные VPS у разных провайдеров и в разных сетях/ASN |
| FastAPI + Telegram-бот | Авторизация устройств, подписки, платежи, назначение нод | Один управляющий VPS |
| PostgreSQL | Пользователи, устройства, ноды и платежи | Тот же управляющий VPS, отдельный Docker-контейнер |
| GOST-ноды | HTTPS CONNECT-прокси с авторизацией пользователей | Отдельные VPS у нескольких провайдеров |
| Канарейка | Проверка доступности нод из российской сети | Отдельная точка проверки в РФ |
| Backup | Ежедневная резервная копия PostgreSQL | Внешнее S3-хранилище или второй сервер |

Начальная конфигурация: два API reverse proxy, один управляющий сервер и минимум три GOST-ноды — две рабочие и одна резервная. API proxy соединяются с управляющим VPS по private tunnel (например, WireGuard); HTTP-порт FastAPI не доступен из интернета и firewall принимает backend-трафик только от этих proxy. На API proxy не размещаются PostgreSQL, Telegram-бот, платёжные секреты или бизнес-логика. Количество GOST-нод увеличивается по загрузке и фактическому трафику.

В production `TRUSTED_PROXY_CIDRS` содержит ровно два host CIDR (`/32` для IPv4 либо `/128` для IPv6), соответствующих WireGuard-адресам ingress A/B. Широкие private ranges запрещены. Ingress заменяет входящий `X-Forwarded-For` на фактический адрес клиента и создаёт новый `X-Request-ID`; поэтому пользователь не может подставить чужой IP для rate limit. Uvicorn не должен самостоятельно доверять forwarded-заголовкам от публичного интерфейса.

Для Telegram используется один HTTPS webhook URL на отдельном поддомене. Одинаковый TLS hostname и маршрут webhook настроены на обоих API proxy, а DNS-провайдер с health-check публикует только адрес доступного proxy. Telegram всегда вызывает один URL; менять webhook при отказе proxy не требуется. Оба proxy пересылают update в один private backend. Обычные два A-записи без health-check не считаются автоматическим failover.

## 3. Пользовательский сценарий

1. Расширение создаёт `device_id`; backend независимо генерирует `telegram_start_token` для одноразовой Telegram-ссылки и `pairing_session_token` для polling расширения.
2. Пользователь открывает бота по ссылке с `telegram_start_token`; backend атомарно привязывает Telegram к устройству, одноразово погашает этот token и запускает trial.
3. Расширение получает результат привязки только по `pairing_session_token`. После привязки backend создаёт третий, независимый `device_token`. При первом создании пользователя также создаются его постоянные `proxy_username` и `proxy_password`.
4. Backend автоматически закрепляет пользователя за рабочей нодой с минимальной относительной загрузкой.
5. Пользователь нажимает «Включить VPN»; расширение получает через `/api/status` адрес текущей ноды и proxy credentials пользователя.
6. При окончании trial расширение отключает прокси и предлагает оплату.
7. После webhook Robokassa backend продлевает подписку; повторный webhook не меняет срок повторно.
8. При блокировке ноды backend назначает пользователю новую рабочую ноду. Расширение получает её через `/api/status` и переключается автоматически.

## 4. Требования к Chrome-расширению

- Manifest V3.
- Разрешения: `proxy`, `storage`, `alarms`, `webRequest`, `webRequestAuthProvider`.
- `host_permissions`: `["<all_urls>"]` для proxy-авторизации через `onAuthRequired`.
- Включение прокси через `chrome.proxy.settings` в режиме `fixed_servers`, схема `https`.
- Передача GOST-логина и пароля через `chrome.webRequest.onAuthRequired` только для proxy-запросов текущей ноды.
- Фоновая проверка `/api/status` через `chrome.alarms`: при включённом VPN — не чаще одного раза в минуту.
- В build-конфигурацию включаются два HTTPS URL API proxy. Их домены включаются в `bypassList`, чтобы расширение могло получить новую ноду при отказе текущей GOST-ноды.
- Расширение сначала обращается к primary API proxy, а при timeout, сетевой ошибке, `408` или `502/503/504` пробует второй URL с ограниченным exponential backoff. `429` соблюдается глобально по `Retry-After` и не обходится через второй proxy; остальные `4xx` также не переключают proxy.
- Оба API proxy разворачиваются, проходят TLS/health/fallback-проверку и только после этого начинается browser E2E и deployment расширения.
- Локально хранятся `device_id`, `device_token`, текущая нода и proxy credentials пользователя.
- Если `/api/status` возвращает другой адрес ноды, расширение автоматически обновляет `chrome.proxy.settings` без действий пользователя.
- Интерфейс: статус, кнопка включения и выключения, срок доступа, оплата; выбор локации — только для платных пользователей.
- В popup не передаются `device_token`, proxy password и `device_id`; последний остаётся внутренним публичным идентификатором установки.
- Ссылка «Пользовательское соглашение» размещается в настройках. До утверждения текста и production URL она видима, но не ведёт на placeholder либо несуществующий внешний документ.

## 5. Авторизация и доступ

| Механизм | Требование |
|---|---|
| `telegram_start_token` | Одноразовый секрет только для Telegram deep link. Генерируется CSPRNG, имеет короткий TTL, атомарно погашается при привязке; в БД хранится только versioned hash. Не принимается endpoint’ом polling. |
| `pairing_session_token` | Независимый секрет, известный только расширению и используемый только для `/api/pairing/status`. Имеет тот же ограниченный TTL; в БД хранится только versioned hash. Не помещается в Telegram URL. |
| `device_id` | Публичный UUID установки. Не является паролем. |
| `device_token` | Третий независимый секрет для каждого устройства. Генерируется только после Telegram-привязки и используется в `Authorization: Bearer` при запросах к FastAPI. В БД хранится только versioned hash. Не совпадает с двумя pairing-токенами. |
| Proxy credentials | Одна уникальная пара `proxy_username` / `proxy_password` на пользователя. Работает на всех активных GOST-нодах и не меняется при переключении ноды. |
| Лимит устройств | Не более 3 записей `devices.status=active` на пользователя; конкурентная проверка выполняется транзакционно. |
| Отзыв устройства | Backend переводит устройство в `revoked` и прекращает принимать его `device_token`. Proxy credentials остаются общими для пользователя. |

Выбранная схема не позволяет отозвать proxy-доступ только у одного устройства: если сохранённые credentials пользователя утекли, для полного отзыва требуется сменить пароль всего пользователя и синхронизировать его на всех нодах.

## 6. Ноды, синхронизация и автоматическое переключение

- При первой привязке backend закрепляет пользователя за активной нодой с минимальной относительной загрузкой: `назначенные пользователи / capacity_users`.
- В нагрузку входят пользователи с действующим trial или paid access, у которых сохранён соответствующий `assigned_node_id`. Кандидаты — только `active` ноды со свободной capacity; при равном коэффициенте выбирается меньший `nodes.id`.
- Выбор и сохранение выполняются транзакционно с блокировкой candidate node и повторной проверкой capacity, чтобы параллельные регистрации не заняли одно последнее место несколько раз.
- Закрепление сохраняется в `users.assigned_node_id`; нода не меняется при каждом запросе.
- Отдельный сетевой балансировщик перед GOST-нодами не используется: backend выполняет логическое распределение и `/api/status` возвращает пользователю конкретную назначенную ноду.
- Платный пользователь может вручную выбрать активную локацию. При этом меняется только `assigned_node_id`; логин и пароль остаются прежними.
- Credentials всех пользователей с действующим trial или подпиской автоматически синхронизируются на все активные ноды.
- При добавлении, блокировке или окончании доступа пользователя список credentials на нодах обновляется автоматически.
- Endpoint `/internal/nodes/{id}/credentials` доступен только по HTTPS и требует отдельный секретный токен конкретной ноды.
- Endpoint возвращает полный snapshot с `revision`, `generated_at`, `snapshot_valid_until` и списком credentials. Одинаковое содержимое имеет одну revision; старый ответ не может заменить уже применённую текущую revision.
- После первого snapshot sync-agent постоянно держит условный `GET .../credentials?wait_seconds=20`. Backend проверяет источник revision каждые 0,5 секунды и немедленно отвечает `200`, если список или статус изменился; при отсутствии изменений завершает long poll через заданный срок ответом `304` с новым lease. После успешного ответа агент без дополнительной периодической паузы открывает следующий long poll.
- Sync-agent валидирует snapshot, записывает временный auth-файл, атомарно заменяет рабочий файл и только после успешного reload GOST отправляет идемпотентный ack в `POST /internal/nodes/{id}/credentials/ack`.
- Backend считает revision применённой на ноде только после ack. Повтор ack той же revision возвращает успех и не создаёт повторных действий.
- Для новой revision backend задаёт 15-секундное ack-окно. Worker считает пропущенные окна, не сбрасывая счётчик повторной выдачей той же или более новой revision. После третьего пропуска active-нода становится `blocked`. Отдельно active-нода блокируется после 75 секунд без успешного ack/условного обновления lease либо после окончания подтверждённого lease.
- После автоматической блокировки worker идемпотентно переносит пользователей на active-ноды с доступной capacity. Пользователь, запросивший `/api/status` раньше завершения batch, также немедленно получает обычный failover; если capacity нет, `assigned_node_id` очищается и возвращается `NO_ACTIVE_NODE`.
- Последний корректный snapshot действует только до `snapshot_valid_until`. Если новый snapshot получить или применить не удалось, после этого времени sync-agent автоматически удаляет/отключает все пользовательские credentials и оставляет только отдельную техническую credential канарейки.
- Вручную выполняются только добавление новых нод и удаление либо отключение старых.

### Проверка из России

- Канарейка из российской сети проверяет каждую ноду не реже одного раза в минуту через реальное подключение к GOST.
- Одна проверка использует минимум два независимых HTTPS target. Успех фиксируется, если доступен минимум один target; одинаковый сбой target/DNS через разные ноды считается `inconclusive` и не увеличивает счётчики нод.
- Каждый результат имеет уникальный `check_id`. Backend сохраняет identity события; повтор того же `check_id`, в том числе с изменённым временем или телом, возвращает прежний успешный результат и не меняет счётчики, статус, назначения или уведомления.
- После трёх последовательных подтверждённых node-specific ошибок нода получает статус `blocked`.
- Администратору отправляется уведомление в Telegram.
- Пользователи заблокированной ноды автоматически переводятся на активную ноду с минимальной относительной загрузкой.
- `/api/status` возвращает пользователю новый `host` и `port`; расширение переключается автоматически.
- После трёх последовательных успешных проверок нода получает `recovery_ready=true`, но возвращается в `active` только после ручного подтверждения администратора.

## 7. Минимальная модель PostgreSQL

PostgreSQL 16+, миграции Alembic, даты — `TIMESTAMPTZ` в UTC. Порт `5432` не открывается в интернет. Системные настройки и секреты хранятся в `.env`.

### 7.1. `users`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID, PK | Внутренний ID пользователя |
| `telegram_id` | BIGINT, UNIQUE | Telegram-аккаунт |
| `status` | VARCHAR | `active` / `blocked` |
| `trial_expires_at` | TIMESTAMPTZ, NULL | Окончание trial; повторно не создаётся |

| `assigned_node_id` | UUID, FK -> `nodes` | Закреплённая нода |
| `node_selection_mode` | VARCHAR | `auto` / `manual` |
| `proxy_username` | VARCHAR, UNIQUE | Уникальный логин пользователя на всех нодах |
| `proxy_password_ciphertext` | BYTEA | Зашифрованный пароль пользователя |
| `proxy_password_key_id` | VARCHAR | Версия AES-256-GCM ключа для dual-read ротации |
| `created_at` | TIMESTAMPTZ | Дата создания |

### 7.8. Служебные таблицы этапа 1

- `node_auth_tokens` и `canary_auth_tokens`: только HMAC-hash, `key_id`, срок и статус `current/next/revoked`; raw token хранится только у соответствующего агента.
- `canaries`: идентичность, статус и время последнего отчёта точки проверки.
- `outbox_events`: уникальный idempotency key, тип/aggregate, минимальный JSON payload, попытки, время следующей попытки и итог без сохранения секретного текста ошибок.

API process не исполняет scheduler. Ровно один worker удерживает PostgreSQL advisory lock и обрабатывает outbox через `FOR UPDATE SKIP LOCKED`. Второй worker не становится scheduler.

### 7.10. `protocol_credentials` — резерв для новых протоколов

Архитектура должна предусматривать отдельную таблицу `protocol_credentials` для хранения доступов пользователя к разным протоколам, включая GOST и будущие Xray-протоколы.

## 9. Платежи Robokassa

- Для MVP доступен один тариф `vpn_30d`: 29 900 копеек (299 RUB), срок 30 дней.
- ResultURL использует HTTP POST (`application/x-www-form-urlencoded`), Password #2 и SHA-256. Успешный ответ — `OK{InvId}`.
- Backend проверяет подпись webhook по секрету Robokassa.
- `/api/payments/create` требует `Idempotency-Key`. Повтор с тем же пользователем, ключом и request body возвращает сохранённый счёт/URL без создания нового платежа; тот же ключ с другим body получает conflict и не меняет БД.
- Сумма, тариф и срок сверяются с данными платежа и настройками `.env`.
- Платёж блокируется в транзакции; `status = paid` и уникальный `webhook_hash` исключают повторное продление.

```text
new_end_date = max(now, current_end_date) + tariff_period
```

Повторный корректный webhook получает успешный ответ, но не изменяет `subscription_expires_at` повторно.

Production-платежи, production credentials Robokassa и реальное списание денег запрещены, пока владелец продукта и ответственный за бухгалтерию/право письменно не утвердят: состав и формат фискального чека, налоговый режим/НДС, данные покупателя, оферту, порядок возврата и сроки хранения платёжных документов. До этого разрешены только локальные fixtures и test mode Robokassa.

## 10. Развёртывание и резервное копирование

| Сервер | Контейнеры / сервисы |
|---|---|
| API proxy A и B | Публичный TLS reverse proxy и WireGuard/private tunnel к backend; разные провайдеры/ASN |
| Управляющий VPS | FastAPI, Telegram-бот, PostgreSQL, внутренний HTTP endpoint, backup cron |
| Каждая GOST-нода | GOST HTTPS proxy, sync-agent для получения общего списка credentials |
| Точка проверки в РФ | Канарейка для регулярной проверки нод и отправки результата backend |

- Ежедневный `pg_dump` в сжатом формате.
- Копия шифруется и отправляется во внешнее S3-хранилище или на второй сервер.
- Хранение минимум 14 ежедневных копий; уведомление при ошибке backup.
- Не реже одного раза в месяц выполняется тестовое восстановление.
- Целевые показатели: RPO не более 24 часов, RTO не более 4 часов; соответствие подтверждается restore-тестом.
- `DATABASE_URL`, токены, ключ шифрования, тарифы, trial, лимит устройств и интервалы проверок задаются в `.env`; `.env` не хранится в Git.
- До browser E2E и deployment расширения оба API proxy должны пройти: TLS-проверку, health backend, переключение primary→fallback, проверку прямой недоступности FastAPI из интернета и сверку обоих доменов с `bypassList` подписанной сборки.
- До production webhook оба API proxy должны принимать один Telegram webhook hostname; DNS health-check должен исключать отказавший proxy, а тестовый update — доходить через каждый из них.

### 10.1. Модель угроз MVP

- Украденный `device_token`: токен хранится только как HMAC-SHA-256 hash в backend, отзывается по устройству и не совпадает с pairing-секретами.
- Пересланная или повторно использованная Telegram-ссылка: start token одноразовый, имеет TTL и атомарно погашается.
- Утечка общего proxy-пароля: пароль зашифрован AES-256-GCM, но технически работает на всех active-нодах; аварийная мера — ротация пароля пользователя и подтверждённая синхронизация всех нод.
- Поддельный или повторный Telegram/Robokassa/canary webhook: проверяется отдельный secret/signature, а update/payment/check обрабатывается идемпотентно.
- Компрометация GOST-ноды: на ней нет БД и ключей backend; credentials имеют конечный lease, а нода блокируется и удаляет пользовательский snapshot.
- Компрометация API proxy: на proxy нет бизнес-логики и прикладных секретов; origin принимает трафик только через private tunnel от разрешённых proxy.
- Отказ DNS или общего backend остаётся точкой отказа MVP и покрывается мониторингом, backup и эксплуатационным runbook, а не вторым writable backend.

## 11. Критерии приёмки

1. Расширение устанавливается без локального клиента и подключается к GOST по HTTPS.
2. После Telegram-привязки пользователь получает trial только один раз.
3. Telegram deep link, polling привязки и постоянная авторизация используют три независимых секрета; каждое устройство авторизуется отдельным `device_token`, лимит устройств и отзыв контролируются backend.
4. Каждый пользователь имеет одну уникальную пару proxy credentials, работающую на всех активных нодах.
5. При смене ноды proxy credentials пользователя не меняются.
6. Credentials активных пользователей автоматически синхронизируются на все активные ноды через защищённый versioned long-poll snapshot; применение атомарно подтверждается ack, stale credentials закрываются после lease, а нода с тремя пропущенными ack-окнами или просроченным heartbeat автоматически блокируется с переносом пользователей.
7. Пользователь закрепляется за нодой; новые пользователи распределяются равномерно по относительной загрузке.
8. Платный пользователь может выбрать доступную локацию; trial-пользователь — нет.
9. После нескольких ошибок канарейки, трёх пропущенных ack-окон или stale heartbeat нода получает статус `blocked`, а пользователи переводятся на рабочую ноду; Telegram-уведомление обязательно после реализации канарейки/alert worker.
10. Расширение работает с backend через два развёрнутых API proxy, переключается на доступный URL и затем получает новую GOST-ноду через `/api/status`; Telegram webhook использует один health-checked домен поверх тех же двух proxy.
11. Создание счёта и webhook Robokassa идемпотентны; повтор не создаёт второй счёт и не продлевает подписку дважды. Production-платежи заблокированы до утверждения чеков, налогов и возвратов.
12. Повтор результата канарейки с тем же `check_id` не меняет состояние ноды повторно.
13. Фоновая проверка выполняется через `chrome.alarms`, proxy-auth — через `onAuthRequired`, `webRequestAuthProvider` и `host_permissions: ["<all_urls>"]`.
14. PostgreSQL и FastAPI origin недоступны из интернета; ежедневный backup создаётся и успешно восстанавливается.
15. Полная цепочка проходит без ручного изменения БД: установка -> Telegram -> trial -> VPN -> автоматическая смена ноды -> test-mode оплата -> продление.

## 12. Не входит в MVP

- Системный VPN для приложений вне браузера.
- Xray, VLESS, Reality, Marzban и собственный desktop-клиент.
- Автоматическая покупка и удаление VPS через API хостеров.
- Сложная аналитика трафика, реферальная система и мобильные приложения.
- Гарантированный срок модерации Chrome Web Store.

**Приоритет разработки:** сначала рабочая сквозная цепочка, автоматическое переключение нод и безопасность доступа, затем масштабирование.
